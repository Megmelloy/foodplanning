Table Sync
Design Document

Architecture, component design, data, security, and delivery notes for the group dining planner.

Team: Ryan, Megan, Kareem, and Calvin

1. Introduction

This document describes the design of Table Sync, the food-planning project in this repository. It records the current architecture, user flows, data structures, external integrations, quality goals, and verification approach. It is intended for the project team, instructors/reviewers, and future maintainers.

The primary scope is the implemented social-dining planner: a group enters a public area and dinner time, records individual tastes, creates a cuisine shortlist, votes on one device, and may export a calendar event. The repository also contains a legacy, opt-in AI meal-planning endpoint. It is documented here for completeness, but it is not connected to the current Table Sync interface.

This is a small-group, single-device application, not a restaurant booking system. It does not currently have user accounts, a database, persisted plans, cross-device participation, outbound invitations, or verified restaurant listings.

2. System Overview (Architectural Design)

The application is a Next.js App Router project using React and TypeScript paired with a C# ASP.NET backend. The social-dining experience is implemented as a client-rendered page. Its domain calculations and validation are synchronous TypeScript functions; no application server request is made to build or vote on a social-dining plan. The separate meal-plan route runs on the server and can call the OpenAI Responses API only when explicitly enabled and configured.

5. Detailed Component Designs (Detailed Design)

5.1 Lobby Service

5.1.1 Overview

Stateful service that creates temporary lobbies which track present users. A user client joins a lobby with a pre-signed invite link. Server sees this, checks which lobby that link is for, then adds the client to a lobby, giving them a token representing their status as a member of that lobby.

A client can join anonymously, being prompted for a name to represent the client user in the lobby for others, or can join using an existing user account. If an account is used, the server automatically uses existing saved user data where possible. Any user can create a lobby, becoming the lobby's Organizer. They can kick other participants, create invite links, and start the recommendation phase. A lobby will time out after 2.5 hours of inactivity, removing all state for that specific lobby from the server.

Taste profiles and organizer-specified location data are gathered. On action from the organizer to start analyzing, participant data is sent to Recommendation Service. The returned venues are then presented to all participants.

5.1.2 Design Considerations

  • Lobby state stored serverside via in-memory key-value store (IMemoryCache). IMemoryCache only works with a single service instance, and a restart/deploy clears lobbies. Can use Redis in future if significant scaling is needed.
  • Members use polling to be updated on lobby state.
  • Changes to each lobby are serialized by per-lobby SemaphoreSlim; a version number is kept for change detection when polling.
  • 2 token types: invite and member. Organizer actions validate via checking role assigned to the member token.
  • Fixed stages that reject out-of-order actions: Open > Recommending > Voting > Finalized; new stages can be implemented in future as needed.
  • Search area set by Organizer.

5.2 Taste Profiles

5.2.1 Overview

Important data structure that represents the compiled preferences and restrictions of an individual user to be used by the recommendation service. Not tied with user accounts: while a user account can have an associated taste profile, a taste profile does not require a user account. A taste profile, once constructed, can be saved to a user account to be reused later.

A taste profile is constructed via asking the user to choose “Love”, “Ok”, or “Skip” on a series of types of cuisines (e.g. Italian, Chinese, American) and can be updated to include any other notable traits that can be discerned in venue data available via public APIs, price preferences, then submit any dietary restrictions.

5.2.2 Design Considerations

  • Shared data model across client and server. TypeScript types are generated from ASP.NET API description.
  • Versioned JSON to allow loading saved profiles after updates to schema.
  • Distinction between hard limits (dietary restrictions, max price, skip) and preferences.
  • Passed via snapshots: updating a saved taste profile does not automatically change the copy of that taste profile already present in a lobby.
  • Information kept private from other users; only used in recommendation service.

5.3 Recommendation Service

5.3.1 Overview

Provided with taste profiles and location data/preferences (location & max distance from location). Gets venues in the area, eliminates any that don't match with taste profiles. Sends subsequent shortlist of venues along with combined preferences and restrictions from all member taste profiles and any other relevant data to external LLM provider along with appropriate instruction to create a final ranked shortlist. Returns the resulting chosen venues, ranked.

5.3.2 Design Considerations

  • Stateless. Uses exclusively the data passed to it on a call.
  • Minimize costly API calls where necessary via internal rate limiting and caching. Caching belongs to VenueProvider, allowing RecommendationService to stay stateless.
  • LLM's role should be minimized: as much of the recommendation work as possible should be done algorithmically before sending the resulting shortlist to an LLM to rank.
  • Require schema-matching JSON output from LLM and validate data (only accept venue IDs present in the list it was given). Limit token usage and wait time.
  • Only send combined preferences to LLM, not individual profiles.
  • When nothing matches, report the restriction that ruled out the most venues to report back to end users.

5.4 User Account Service

5.4.1 Overview

Allows users to create accounts on the app, saving basic user information, preferences, and taste profiles. Optional — users do not need an account to access core functionality; serves as a quality of life feature for repeat users. Authentication is handled via external OAuth providers to reduce security and database requirements.

5.4.2 Design Considerations

  • Optional everywhere: every flow must work without an account.
  • No passwords stored in DB — validation handled via external OAuth providers.
  • Sessions kept in secure httpOnly cookies with CSRF protections on routes that change data.
  • Deleting an account also deletes all saved taste profiles.

5.5 User Interface

5.5.1 Overview

TypeScript Next.js web app deployed to a user's internet browser, device-agnostic. Interfaces with the rest of the app via HTTP REST. Used to construct a user's Taste Profile, show lobby participants (and allow the Organizer to manage it), and to present recommended venues.

5.5.2 Design Considerations

  • One flow for both Organizer and Participant in lobby; organizer just gets extra controls added.
  • LocationPicker component is only for Organizers.
  • Survives refreshing the page on a browser — member token kept in browser storage.
  • Location gathered via browser's location by default, allowing user to override by specifying a given location.
  • Errors shown inline next to fields.

7. User Interface Design (Detailed Design)

The interface adapts dynamically based on the participant's role in the lobby session:

  • Host (Organizer) View:
    1. Create a session utilizing HTML5 Geolocation with manual ZIP/postal code fallback.
    2. Generate and copy pre-signed invite links and manage the lobby roster.
    3. Input cuisine preferences (Love, Ok, or Skip), maximum price comfort, and hard dietary restrictions.
    4. Trigger recommendation analysis, review the interactive ranked venue shortlist, and lock in the final venue choice.
  • Guest (Participant) View:
    1. Join session via `/join/[token]` anonymously with a display name or via OAuth sign-in (with saved profile pre-fill).
    2. Input cuisine preferences (Love, Ok, or Skip), maximum price comfort, and hard dietary restrictions.
    3. Review the live lobby roster, ranked venue shortlist, finalized venue link, and `.ics` calendar export.

8. Error Handling and Exception Management (Detailed Design)

The server returns consistent ApiError objects containing a safe user message, machine-readable code, and requestId. Validation errors identify fields inline without exposing internal server details. Expected error cases include expired or invalid invite links, incomplete profiles, out-of-order stage actions, no eligible restaurants, provider rate limits, provider timeouts, and invalid AI output.

External calls use strict timeouts and limited retries with backoff. If LLM text generation or ranking fails, RecommendationService gracefully falls back to DeterministicRanker scores without disrupting the user interface. If no restaurant satisfies all hard constraints, the application reports the specific restriction that ruled out the most venues (for example, “No restaurants within 5 miles support both Vegan and Nut-Free requirements. Please expand the search radius or adjust restrictions.”) rather than failing generically.

9. Security Design (Detailed Design)

  • Invite and member tokens are cryptographically random, difficult to guess, stored as SHA-256 hashes (tokenHash) on the server, and expire automatically.
  • Organizer-only actions (creating invites, kicking members, starting recommendations, finalizing a venue) validate the organizer role assigned to the caller's memberToken.
  • Accounts are optional, and guests can join a lobby without one. Repeat-user authentication is delegated to external OAuth 2.0 providers so no passwords are stored in the database. Sessions are kept in Secure, httpOnly cookies with CSRF protections on state-changing routes.
  • Every API route validates input schemas and verifies that referenced records belong to the same lobby or account. Public endpoints are rate-limited and protected against automated abuse.
  • All traffic uses HTTPS; secrets remain in environment-managed server configuration, and database access uses least-privilege credentials.
  • Structured server logs avoid dietary details, raw invite/member tokens, and unnecessary personal information. Stored data is minimized: lobbies expire after 2.5 hours of inactivity and are purged, and deleting an account cascades deletion to all saved taste profiles.

10. Performance Optimization (Detailed Design)

Active lobby state is held in fast server-side memory (IMemoryCache, with Redis support via LobbyRepository) and uses lightweight version numbers so polling clients only process state deltas. Per-lobby concurrency is serialized via fine-grained SemaphoreSlim locks, and the lock is released while external recommendation calls execute so lobby polling is never blocked.

To minimize latency and external API costs, VenueProvider caches upstream venue search results by area and category. RecommendationService performs deterministic filtering and scoring in memory first, sending at most ~10 candidate venues and aggregated group preferences to the LLM with bounded token limits and a strict timeout.

11. Deployment Architecture (Detailed Design)

The Table Sync production architecture follows a decoupled, cloud-hosted multi-tier topology separating the device-agnostic Next.js TypeScript web client from the stateful C# ASP.NET Core Web API backend, backing data stores, and external service providers.

OpenAPI Contract Synchronization OpenAPI 3.0 JSON → TypeScript types Generates shared client TypeScript definitions (TasteProfile, Lobby, RankedVenue, ApiError) directly from the ASP.NET API specification.
Venue Provider (VenueProvider → Google Places API) HTTPS GET/POST, JSON Queries candidate venues by SearchArea (coordinates or postal code and radius) and mapped cuisine categories. Caches venue lookups and enforces timeouts with retry backoff.
LLM Ranker (LlmClient → OpenAI API) HTTPS POST, Structured JSON Schema Sends aggregated GroupPreferences (never individual profiles) and the top ~10 deterministically filtered venues. Validates returned venue IDs against the candidate set and falls back to DeterministicRanker on timeout or invalid output.
Browser Geolocation, Maps & Calendar Export HTML5 Geolocation, HTTPS Maps URL, .ics file Captures organizer location with manual ZIP fallback; opens external Google Maps links for recommended venues; downloads an RFC 5545 .ics event upon finalization.

13. Testing Strategy (Detailed Design)

Verification spans unit, integration, contract, and end-to-end acceptance testing across both the Next.js TypeScript frontend and the C# ASP.NET Core backend. Automated test suites mock external providers so tests run deterministically offline without incurring paid API charges.

  • Backend unit tests (xUnit & Moq): verify LobbyService stage transitions (Open → Recommending → Voting → Finalized), 1–15 member limits, SemaphoreSlim concurrency locking, 2.5-hour inactivity expiration, GroupPreferences aggregation, hard dietary/skip filtering, emptyReason diagnostics, and LlmRanker fallback to DeterministicRanker on timeout or invalid venue IDs.
  • Frontend unit and component tests (Node test runner / Vitest): verify client-side TasteProfile.validate() logic, versioned JSON serialization, useLobby polling updates, ClientSession storage across refreshes, role-gated organizer controls, and .ics calendar generation.
  • API and integration tests (ASP.NET WebApplicationFactory): test full HTTP REST workflows against in-memory/Redis lobby stores and containerized PostgreSQL databases, verifying hashed invite/member token checks, OAuth session cookie and CSRF guards, and cascading profile deletion on deleteAccount.
  • End-to-end acceptance testing (Playwright): simulates an Organizer and multiple concurrent Participants across separate browser contexts creating a lobby, joining via /join/[token], submitting taste profiles, reviewing the ranked venue shortlist, and finalizing the selection.

14. Maintenance and Support (Detailed Design)

The project is maintained in Git on GitHub (Megmelloy/foodplanning) using feature branches, pull request reviews, and automated Continuous Integration checks.

  • Continuous Integration and release management: Pull requests and pushes to main trigger .github/workflows/ci.yml, enforcing clean code formatting (Prettier and dotnet format), static analysis (ESLint and .NET analyzers), OpenAPI-to-TypeScript type synchronization, unit/integration test suites, and production builds prior to deployment promotion.
  • Schema versioning and modular extensibility: TasteProfile payloads include a schemaVersion attribute so saved profiles in PostgreSQL can be migrated forward as cuisine or dietary options evolve. Core services depend on interfaces (LobbyRepository, AccountRepository, VenueProvider, VenueRanker), allowing maintainers to transition from single-instance IMemoryCache to distributed Redis or swap venue/LLM providers without rewriting domain logic.
  • Observability, privacy auditing, and dependency hygiene: Server operations emit structured logs correlated by requestId for provider outages, fallbacks, and error spikes while redacting dietary details, raw invite/member tokens, and personal data. Inactive lobbies are automatically purged after 2.5 hours, and dependencies are audited regularly via npm audit and dotnet list package --vulnerable.

15. Glossary

Term Definition
Table Sync User-facing name of the group dining planner application.
Lobby A stateful, temporary session (expiring after 2.5 hours of inactivity) where an Organizer and up to 15 Participants gather taste profiles and select a restaurant.
Organizer The user who creates the lobby, sets the search area, manages invite links and participants, triggers recommendations, and finalizes the venue pick.
TasteProfile A versioned structure recording a user's cuisine ratings (Love, Ok, Skip), maximum price level (1–4), and hard dietary restrictions.
VenueProvider Backend abstraction (e.g., GooglePlacesProvider) that searches and caches candidate restaurants within the Organizer's search area.
DeterministicRanker / LlmRanker Ranking implementations of VenueRanker; filters and scores venues deterministically first, uses an LLM to rank the top shortlist, and falls back to rule-based ranking on error.
.ics RFC 5545 iCalendar file format used for the downloadable dinner event.
