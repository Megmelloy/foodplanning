Table Sync
Design Document

Architecture, component design, data, security, and delivery notes for the group dining planner.

Team: Ryan, Megan, Kareem, and Calvin

1. Introduction

This document describes the design of Table Sync, the food-planning project in this repository. It records the current architecture, user flows, data structures, external integrations, quality goals, and verification approach. It is intended for the project team, instructors/reviewers, and future maintainers.

The primary scope is the implemented social-dining planner: a group enters a public area and dinner time, records individual tastes, creates a cuisine shortlist, votes on one device, and may export a calendar event. The repository also contains a legacy, opt-in AI meal-planning endpoint. It is documented here for completeness, but it is not connected to the current Table Sync interface.

This is a small-group, single-device application, not a restaurant booking system. It does not currently have user accounts, a database, persisted plans, cross-device participation, outbound invitations, or verified restaurant listings.

2. System Overview (Architectural Design)

The application is a Next.js App Router project using React and TypeScript. The social-dining experience is implemented as a client-rendered page. Its domain calculations and validation are synchronous TypeScript functions; no application server request is made to build or vote on a social-dining plan. The separate meal-plan route runs on the server and can call the OpenAI Responses API only when explicitly enabled and configured.

In the social-dining flow, the browser holds all current planning state in React memory. A refresh clears the group and its votes. Google Maps receives a search link containing the selected area, cuisine, and applicable budget wording; dietary needs and individual notes are not included. The user chooses a specific restaurant from Google's results and confirms suitability directly with that restaurant.

5. Detailed Component Designs (Detailed Design)

5.1 Social-Dining Planner Interface

5.1.1 Overview

The planner is the Home client component in src/app/page.tsx. It presents three steps:

  1. Where & when: public area and a future date/time, from now through 365

days ahead.

  1. Tastes: 2–15 numbered participants (the organizer is Person 1), cuisine

preferences, budget, dietary needs, and optional notes. The organizer alone can add or remove guests in this shared-device session.

  1. Vote: up to three cuisine searches, one optional vote per participant,

an organizer tie-break when needed, and final-pick/calendar actions.

The planner owns transient form, plan, vote, error, and selection state. It delegates validation, ranking, tallying, schedule formatting, and calendar generation to src/lib/social-dining.ts.

5.1.2 Design Considerations

  • The interface does not collect names or send invitations; guest labels are

person numbers on the current device.

  • Editing the location, schedule, or preferences invalidates the previously

generated plan and votes so stale results cannot be finalized.

  • An omitted cuisine preference means “Open.” Any participant's “Skip”

excludes a cuisine. The lowest price range selected by anyone informs Maps search wording.

  • Dietary needs and notes are reminders for the group to confirm, not filters

against verified menus. Search results are not guaranteed to match budget, opening hours, distance, accessibility, or group seating.

  • Schedule values are interpreted in the browser's local time zone.
  • With no favorites, the fixed cuisine order provides exploration ideas. If

all cuisines are skipped, the shortlist is empty and voting is unavailable.

  • A finalized choice identifies a cuisine search, not a confirmed venue.

5.2 Social-Dining Domain Logic

5.2.1 Overview

src/lib/social-dining.ts defines the dining types and fixed choices, input parsing, schedule validation/formatting, invitation limits, shortlist generation, vote tallying, and iCalendar text creation. It has no network or database dependency.

5.2.2 Design Considerations

The domain layer validates finite lists and bounds (2–15 participants, 120 characters for the area, 300 for notes, valid cuisine/dietary selections, and a future schedule no more than 365 days away). A person's liked and avoided cuisines cannot overlap. Shortlist generation excludes cuisines skipped by anyone, ranks remaining cuisines by number of likes, resolves equal ranking by the fixed cuisine order, and takes at most three. Vote tallying rejects duplicate options and votes outside the shortlist. Calendar values escape special text characters and represent a two-hour event in local time.

5.2.3 Class Diagram

The types and main operations are shown in section 5.1.3. The domain functions are exported operations, not class methods.

5.3 Legacy AI Meal-Plan API

5.3.1 Overview

POST /api/meal-plan is a server-side compatibility endpoint implemented in src/app/api/meal-plan/route.ts. It accepts a bounded JSON meal-planning request, validates it through src/lib/meal-plan.ts, conditionally calls OpenAI's Responses API, validates the generated plan, and returns JSON. It is not invoked by the current social-dining page.

5.3.2 Design Considerations

  • The endpoint is disabled unless ENABLE_AI_PLANNING=true and a server-side

OPENAI_API_KEY are configured. OPENAI_MODEL is optional.

  • Requests are limited to 4,000 characters; individual and group preference

formats have additional bounds. Plans must contain the requested sequential number of meals (1–7 days), with serving counts from 1–8.

  • Group requests can contain 2–8 anonymous preference profiles. The server

combines them and labels them by person number.

  • Provider calls have a 45-second timeout, request store: false, and cap

generated output tokens. Provider output is parsed and validated before it is returned.

  • AI output can be inaccurate. It is not authoritative allergen, nutrition,

medical, or food-safety advice.

  • The route does not implement authentication, authorization, per-user rate

limits, abuse prevention, or spending controls. The enable flag is a deployment switch, not access control. Keep the route disabled on public deployments until these controls exist.

Social-dining constraints: A group contains 2–15 participants; each participant has a budget of $, $, or $$, unique valid liked/avoided cuisines, a finite set of dietary needs, and at most 300 characters of notes. An omitted vote is allowed. A submitted vote must select one of the generated options. The group summary unions dietary needs and keeps notes associated with person numbers.

The legacy API has a separate payload: PlanningInput contains days, servings, and combined preferences; MealPlan contains one sequentially numbered meal per requested day and a grocery list. The legacy plan is held by the caller and is not saved by this application.

7. User Interface Design (Detailed Design)

The responsive single-page interface uses a three-step progress control and a two-column desktop layout with a group snapshot beside the active step. On narrow screens, content stacks vertically.

+----------------------------------------------------+
| Table Sync                              Small group |
+----------------------------------------------------+
| Dinner, decided together.                           |
| [Where & when]       [Tastes]          [Vote]       |
+------------------------------------+---------------+
| Current step form/result           | Group snapshot|
|                                    | Area and time  |
|                                    | Size and budget|
|                                    | Needs and notes|
+------------------------------------+---------------+

The visual system uses a warm cream background, dark ink text, tomato and herb accents, rounded cards, and large display headings. Inputs are labeled, related choices use fieldsets, current errors use alert semantics, and keyboard focus is visibly outlined. Vote totals and the selected event are presented in the page. Dietary needs and notes are explicitly presented as information to confirm, not verified filters.

8. Error Handling and Exception Management (Detailed Design)

The social-dining UI validates area and schedule before advancing and reports invalid group input inline. The domain parsers return null for invalid untrusted input; domain invariants that should already be guaranteed by validated state (for example, an invalid internal budget or vote) throw an error. User edits clear prior plans and votes rather than retaining stale results.

The legacy API returns JSON error messages with these HTTP statuses:

StatusMeaning
400Malformed JSON or invalid planning input
413Request exceeds the 4,000-character body limit
502Provider failure or invalid/incomplete provider output
503AI feature disabled or server key unavailable
504Provider request timed out

Provider failures are logged server-side with status/timeout context, without logging submitted preferences or API credentials. Errors from the optional provider are reported to the caller; no partial or success-shaped fallback plan is returned.

9. Security Design (Detailed Design)

  • The social-dining flow keeps input in browser memory and does not send it to

the application server. It does not request names. Users are instructed to enter public areas rather than private addresses and avoid sensitive or medical information.

  • Opening a Maps search sends its area, cuisine, and budget wording to Google.

Dietary selections and notes are excluded from that URL.

  • The AI integration is server-side. The API key must be supplied through

OPENAI_API_KEY; it must not be exposed through a NEXT_PUBLIC_ variable. The feature defaults to disabled. The request asks the provider for store: false, which is not a guarantee of zero provider retention.

  • The endpoint validates body size and input/output shapes and applies a

provider timeout. Those protections do not replace authentication, authorization, rate limiting, abuse detection, or spending controls, none of which are implemented.

  • No user authentication, roles, encryption-at-rest, audit trail, or persisted

personal data store exists. Any public deployment should use HTTPS and keep the legacy AI feature disabled until production access and cost controls are added.

  • AI-generated recipes must be checked for allergens, ingredient amounts, and

safe cooking instructions.

10. Performance Optimization (Detailed Design)

The main workflow is client-side and uses bounded arrays: at most 15 people, eight cuisines, and three shortlist options. Schedule validation, shortlist ranking, and vote tallying are small in-memory operations. There is no application database, so indexing and query optimization do not apply. The application does not implement a cache for user plans.

The AI route bounds request size, output tokens, and provider wait time. No throughput or concurrency guarantees are claimed; the route should not be publicly enabled without rate limits and spending controls.

11. Deployment Architecture (Detailed Design)

The project is configured for Node.js 24 LTS and npm. Development runs with npm run dev; a production build uses npm run build, followed by npm run start. The repository configures Next.js builds to use webpack. No specific production host, hardware specification, network topology, or deployment automation is defined.

    Static[Page and static assets]
    Route[Optional meal-plan route]
    Provider[OpenAI API]
    Maps[Google Maps]
    User -->|HTTPS in hosted deployment| App
    App --> Static
    User -->|Optional HTTPS request| Route
    Route -->|HTTPS, only when enabled| Provider

For local development, the social-dining flow requires no API key. The legacy AI endpoint requires OPENAI_API_KEY and ENABLE_AI_PLANNING=true; the model can be selected with OPENAI_MODEL. Secrets belong in server-side environment configuration (locally, .env.local), not committed source or client-visible configuration. Public deployments should leave AI planning disabled until authentication, rate limiting, abuse prevention, and spending limits are implemented.

13. Testing Strategy (Detailed Design)

Tests use Node's built-in test runner with JavaScript test files importing the TypeScript domain modules. Tests do not make paid AI calls.

  • Unit/domain tests: validate planning and meal-plan inputs, schedule

limits, shortlist ranking and skips, Maps URL construction, vote totals and tie behavior, invite limits, calendar output, and meal-plan schema parsing.

  • Integration/system tests: no browser-level end-to-end or deployed-system

suite is currently configured. The AI endpoint is not exercised against a live provider in the test suite.

  • Acceptance testing: use the user flows in sections 5.1 and 5.3 and

confirm restaurant details directly. No automated acceptance framework is configured.

  • Static/build checks: run ESLint, TypeScript type-checking, tests, and a

production build.

Commands (PowerShell):

npm.cmd run lint
npm.cmd run typecheck
npm.cmd test
npm.cmd run build

14. Maintenance and Support (Detailed Design)

The repository is maintained in Git and hosted at Megmelloy/foodplanning. The README documents local setup, feature behavior, privacy notes, checks, and deployment cautions. The project currently has no documented issue-triage policy, support schedule, release cadence, or automated release process.

When changing dining rules, update the associated tests and README behavior notes. When changing the API contract or environment settings, update the meal-plan validation, endpoint tests, and setup/security documentation. Re-run lint, type-check, tests, and production build before a release.
